01 · Architectural Thesis

Five non-negotiable design choices that shape everything downstream.

The BRD describes three products but only one platform problem. The thesis below resolves the structural tensions in the BRD — between ZDR and AI flywheels, between platform ownership and CCaaS plurality, between latency and safety — into a coherent architecture.

01

Overlay, not CCaaS.

The platform never replaces the customer's CCaaS. Adapters subscribe to Genesys, Amazon Connect, Twilio, NICE, Five9 via their real-time and batch APIs. Owning the routing layer would collapse addressable market by ~70%.

02

Operator-of-tenants.

The BPO operates the platform. Each enterprise customer is a tenant beneath. Cell-based isolation: shared cells with row-level + namespace isolation default, dedicated cells with VPC isolation for premium and regulated tenants.

03

ZDR as architecture.

Hot path produces no durable artifacts. All persistence is opt-in, scoped, TTL'd, and subject to per-tenant data residency. PII redaction sits between application logic and the model gateway as a sidecar that cannot be bypassed.

04

Two gateways, one pattern.

Every LLM, embedding, and reranker call passes through the Model Gateway. Every STT and TTS call passes through the parallel Speech Services gateway. Both handle tenant-scoped provider selection, fallback, cost attribution, eval logging, and provider-agnostic streaming. No provider-specific code outside them.

05

Hot path / cold path split.

Latency-critical services run in-region beside the agent and customer. Heavy services (eval, retrain, batch QA) run in cost-optimized regions with explicit data movement contracts. The split is enforced by topology, not convention.

Trade-off acknowledged. ZDR-default actively works against the cross-tenant data flywheel that would otherwise be the BPO's strongest moat. The architecture resolves this with a separate, explicit, opt-in Federation Tier — a contractual and technical layer where consenting tenants exchange anonymized signals (rubric calibration, intent libraries, vertical benchmarks) for commercial credit. Federation is a Phase 2 product; not part of the default data plane.

Trade-off rejected. The BRD implies building a Cognigy-equivalent runtime from scratch. This architecture treats the Conversational AI runtime as a build-or-license decision flagged at component level, not a foregone conclusion. The platform is shaped so that the runtime is replaceable without rewriting the rest of the stack.

What it must do exceptionally well. Three things: (a) ingest from any CCaaS without drift, (b) keep the hot path under stated latency budgets at p95, (c) prove ZDR through audit. The rest is engineering competence; these three are existential.

Where the platform deliberately accepts a worse outcome. Voice quality on tool-calling flows. Latency on jurisdictionally-restricted data paths. Feature parity with single-purpose specialists like Sierra (Conv AI), Cresta (Agent Assist), Observe.AI (Insights). The platform's bet is integration and operator-of-tenants leverage, not best-of-breed in any single product.

What this platform is not.

Strategic boundaries deserve their own visible block. Without explicit limits, scope creep is inevitable.

Not in scope

Not a CCaaS.

The platform overlays customer-owned CCaaS estates. It does not handle ACD routing, IVR, PSTN connectivity, or telephony provisioning. Building these would compete with Genesys, Twilio, NICE, Connect — and lose.

Not in scope

Not a CRM.

CRM context is pulled at call connect via adapters. The platform never persists or manages the system of record. Salesforce, Zendesk, ServiceNow remain the source of truth.

Not in scope

Not a frontier model lab.

The platform does not train foundation models. Provider models are accessed via gateway. Per-tenant fine-tuning of small/distilled models is in scope; pre-training large models is not.

Not in scope

Not on-prem (v1–v3).

Cloud-hosted only. Premium tier offers BYOC (bring-your-own-cloud) for regulated tenants but not on-premise install. On-prem would 3x the surface area.

Not in scope

Not a workforce platform.

WFM, agent payroll, scheduling, attendance, performance management for HR purposes are out of scope. Coaching workflow integration is in scope; HR-grade WFM is not.

Not in scope

Not a single-tenant product.

Architecture refuses single-tenant shortcuts even where they would be expedient. If you cannot ship the feature multi-tenant, defer it to a later phase rather than introduce single-tenant carve-outs.

02 · System Overview

The platform in one diagram.

Eight horizontal layers, three vertical product silos, one control plane. Read top-down: the customer's existing estate is the source of all interaction signal; the BPO operator's UIs are the destination of all platform output. Hot path traffic flows in orange.

Master architecture · L0 customer estate, L1 adapters, L2 real-time data, L3 intelligence, L4 product silos, L5 control plane, L6 data plane, L7 observability, L8 UIs. Hot path in orange.

Read the diagram top-down. Customer estate (L0) is the source of every signal the platform processes. The platform sits between L0 and the BPO operator's UIs in L8. L1 abstracts away CCaaS heterogeneity. L2 turns audio into structured streams. L3 turns structured streams into reasoning. L4 packages reasoning into product features. L5 controls who can do what. L6 stores what little is allowed to be stored. L7 watches everything. L8 exposes it.

The hot path is short. For Agent Assist: L0 → L1 → L2 (STT, sentiment, PII guard) → L3 (Suggestion Engine + RAG + Gateway) → L4 (Live Suggestion Svc) → L8 (Agent Overlay). Five hops. Sub-2s p95 budget split: 200ms STT, 400ms LLM, 100ms RAG, 100ms PII, 200ms transport, 1000ms slack.

L3 is the most expensive layer. Every product depends on it. Every cost optimisation that matters happens here: prompt caching at the gateway (Anthropic native, others via gateway-managed cache), SLM routing for simple intents (Claude Haiku, Gemini Flash, Llama 3.x 8B), aggressive RAG reranking to cut context size, and per-tenant token budgets enforced at the gateway level.

L6 is the smallest layer. By design. The default path through the platform produces no L6 writes. Tenants who opt in to persistence (transcripts, conversation state, evaluation traces, fine-tuning data) sign explicit consent, choose retention windows, and pay incremental storage. The architecture treats stored data as exception, not norm.

03 · Tenancy & Cell Architecture

Three tenant tiers, three cell types, one routing layer.

The BRD specifies "logical default, physical premium" tenancy. The cell architecture below operationalizes this by giving the operator (BPO) three commercial tiers that map cleanly to three different deployment topologies, all routed through a single tenant-aware ingress.

Tier 1 · Standard

Shared cell, row-level isolation.

Default for SMB and mid-market tenants. All tenants share a regional cell. Isolation: row-level security in Postgres, namespace in k8s, prefix in S3, collection in Qdrant, topic in Kafka. Single CMK per cell, tenant-scoped envelope keys. Suitable for non-regulated workloads up to ~10K calls/day.

Tenant routing — how a request finds its cell.

Every inbound request — real-time voice from Genesys, webhook from Salesforce, console login — carries a tenant identifier. The Tenant Router (stateless, deployed at the edge) resolves tenant_id → region + cell_id from a globally-replicated lookup table, then forwards to the appropriate cell's ingress. This is the only globally-replicated state in the system; everything else is regional.

Tenant routing topology · global router fans out to regional cells based on tenant_id resolution.

Why this matters. Three properties fall out of this topology. (1) Tenant data residency is a property of cell placement, not application logic — moving a tenant to ap-south-1 means migrating cell binding, not rewriting code. (2) Adding a new region is a matter of provisioning a new cell template and updating the router, not redeploying the platform. (3) Premium tenant onboarding is a Terraform run, not a quarter-long custom deployment.

A "cell" defined precisely.

v1.0 used "cell" loosely. Precise definition: a cell is one EKS cluster, one Aurora cluster, one set of supporting data services (Qdrant, Redis, Kafka, OpenSearch), one regional VPC (or one tenant-dedicated VPC for Premium), and one set of platform services deployed via ArgoCD ApplicationSet. A region can hold multiple cells. A cell can hold multiple tenants (Standard) or one tenant (Premium). Cell capacity is bounded by k8s control plane limits, Aurora write throughput, and operator cognitive load — practical maximum ~150 tenants per Standard cell at Phase 2 scale.

Tenant migration between tiers and cells.

Tenants move between cells for three reasons: (1) tier upgrade (Standard → Isolated → Premium) as their volume or compliance needs grow, (2) capacity rebalancing when a Standard cell approaches limits, (3) data residency change (e.g., EU-based subsidiary acquired requiring eu-west-1 placement). Migration is non-trivial and gets its own dedicated tooling.

04 · Zero Data Retention Pipeline

ZDR is enforced by topology, not by policy.

A common failure mode is to declare "ZDR by default" while leaving every persistence path enabled and relying on configuration to disable them. This architecture inverts that: persistence paths are disabled by default at the storage adapter level, and explicit per-tenant policy is required to turn each one on. The audit trail records every byte that leaves the hot path.

ZDR pipeline · hot path is in-memory and ephemeral; cold path is gated by per-tenant policy and audit-logged on every write.

The four ZDR enforcement mechanisms.

  1. Storage adapters disabled by default. Transcript writer, recording archiver, conversation logger deployed as separate services, only activated when tenant config explicitly enables them. Default config has all four off.
  2. Network egress controls. Hot-path services run in pods with network policies allowing egress only to in-cell services and approved external endpoints (Anthropic ZDR API, Deepgram on-prem). They cannot write to S3, Postgres, or external storage.
  3. Provider ZDR contracts. Anthropic offers Zero Data Retention API for enterprise. OpenAI offers ZDR contractually. Deepgram offers on-prem. Provider ZDR verified per-tenant and recorded in contract registry.
  4. Audit on every gate crossing. Every byte crossing the persistence gate generates audit log entry: tenant_id, data_type, byte_count, retention_window, CMK_id, requesting_service, justification. Hash-chained and replicated.

The retraining problem, resolved.

The BRD wants ZDR-default and continuous learning from agent feedback. These conflict on their face. Resolution: a separate, opt-in Federation Tier: tenants who want to contribute to model improvement sign a federation agreement, after which a sidecar in their cell forwards anonymized signals to a platform-owned aggregator. Aggregator never sees raw transcripts; signal pairs only.

Concrete components. (1) Federation Sidecar — runs in the tenant's cell, applies k-anonymity (k=20+) and differential privacy (ε≤1.0) to outgoing signals, audited. (2) Aggregator — platform-owned, regionally segregated (US/EU/IN aggregators do not share data), receives only DP-protected signals. (3) Consent Ledger — append-only record of which tenants federated which signal types over which time windows, queryable by tenant. (4) Value-share Meter — tracks federation contributions per tenant for commercial credit. (5) Federated Model Registry — models trained on federated signals are versioned and tenants who federated can pull the resulting model improvements.

For per-tenant fine-tuning (custom STT vocabulary, custom QA rubric), the tenant explicitly opts in to retain training data inside their own cell. Training data never leaves tenant boundary. Models are trained in-cell or on temporary egress to training environment with strict deletion contracts.

Confidence: moderate · Federation Tier is novel and contractually complex. Realistic adoption ~20% of tenants in year 1. Requires external privacy review before launch.

04b · Data Lifecycle & DSR Pipeline

Every byte of opt-in data has a defined end.

Section 04 (ZDR) covers the default — no persistence. This section covers the exception — opt-in persistence — and what happens when a tenant or end-customer demands that data be deleted, exported, or accounted for. GDPR Article 15 (right of access), Article 17 (right to erasure), Article 20 (right to data portability), and equivalent rights in CCPA/HIPAA require the platform to fulfill DSRs (Data Subject Requests) within statutory windows — typically 30 days. The architecture must operationalize this, not just claim compliance.

Data lifecycle DSR fan-out · single delete request reaches seven stores, audited end-to-end.

Retention is not optional, it is a tenant config.

Every persistent store has a tenant-scoped TTL policy. Defaults: transcripts 90 days, QA scores 12 months, conversation state 30 days, eval traces 30 days, audit logs 7 years (regulatory minimum). Tenants can shorten any TTL but cannot extend audit log retention below 7 years. TTL enforcement runs as a daily job in each cell, with audit log entries for every batch delete.

For tenants who require shorter retention than the regulatory minimum on audit logs (e.g., aggressive data minimization stance), the platform records a compliance exception in the contract registry and the tenant accepts the regulatory risk in writing.

Three DSR types the platform handles.

Erasure (Article 17): Fan-out delete across seven stores as diagrammed above. Backups retain data for an additional ~30 days but are tombstoned and purged at next backup rotation. Tenants notified of completion with cryptographic attestation.

Access (Article 15): Aggregate all data for end-customer X across stores into a structured export. Delivered as encrypted JSON+attachments to the tenant within 14 days. Tenant is responsible for forwarding to the end-customer.

Portability (Article 20): Same as Access but in a standard machine-readable format (CSV + JSON + audio files). Exported to a tenant-specified S3 location.

SLA: Internal 14 days, external 30 days (GDPR statutory). The platform's contracts pass this SLA to tenants.

DSR is harder than it looks — three failure modes

(1) Identifier matching. An end-customer might be referenced by phone number, email, account ID, or just a transcript fragment. The Identifier Resolution service maintains a per-tenant mapping but cannot find data that was never linked to a known identifier. (2) Vector embedding deletion. Qdrant supports payload-filter delete but cannot guarantee removal of derived embeddings from a model that was fine-tuned on the data. The platform's contractual position: fine-tuned models are a separate consent boundary, with their own deletion-or-retraining workflow on DSR. (3) Backup tombstoning. Backups retain deleted data until rotation. Tenants must be told this in plain English at contract time; "deleted in 14 days but recoverable from backup for 30 more" is the truth.

05 · Model Gateway

One service that every LLM, embedding, and reranker call passes through.

The model gateway is the most important service in the platform. It is the only place that talks to LLM providers, and the only place that decides which provider handles a given call. Centralizing this gives the platform tenant-scoped model selection, fallback, prompt caching, cost attribution, eval logging, and provider-agnostic streaming — without bleeding provider-specific code into every product service. Audio I/O (STT, TTS) sits behind a parallel Speech Services gateway with the same pattern — see 05b.

Model Gateway · seven-step pipeline with provider fan-out and tenant-scoped configuration.
Architectural choice

Build on LiteLLM, do not adopt it as-is. LiteLLM (open-source, Apache 2.0) provides provider abstraction for ~100 LLM providers and saves significant engineering work. The gateway above adds tenant-aware routing, semantic caching, SLM classification, structured Langfuse telemetry, and compliance gates LiteLLM does not provide. Recommendation: fork LiteLLM, build platform-specific layers as middleware, contribute generic improvements upstream.

Pipeline ordering matters — SLM router before cache, not after

The gateway routes complexity-classifies before looking up the cache. The cache key is hash(prompt + model_class + prompt_version), not just hash(prompt). Reason: if cache lookup happened first, every cache hit would return whatever model originally responded — typically the large model, since cache populates from real responses. The platform would pay cache-storage cost but lose the SLM cost optimization. Putting the router first means a simple query routes to Haiku, then we look for a Haiku-class cached response, and we cache new Haiku responses for re-use. The gateway pays a ~30ms classifier latency on every call to earn ~70-80% cost reduction on simple queries.

Realistic cache hit ratio targets (revised down from v1.0)

Original targets of "≥35% on Insights, ≥15% on Conv AI" were optimistic. Insights workloads have high prompt similarity per rubric parameter (same prompt template) but low transcript similarity across calls, so semantic cache hit is in the 15–25% range realistically. Conv AI conversation turns are high-variance; cache hit is rarely above 5–10% except on greeting/disambiguation moments. Anthropic's native prompt caching helps differently — it caches prompt prefixes server-side, cutting input token cost by ~90% for the cached portion. Lean on prompt caching for input cost reduction; don't expect response-level cache hits to be the main lever.

Prompt versioning is a first-class concept

Every prompt has a semantic version. Cache keys include the version, so changing a prompt invalidates its cache entries (no stale responses to changed prompts). Prompt versions are stored in the Config Service alongside tenant config, promoted dev → staging → prod via PR. When a model provider releases a new model version (Claude Sonnet 5, GPT-5), the gateway treats it as a new model_class for caching purposes — old cache entries remain valid for the old class, new entries populate for the new class. This is how the platform absorbs model upgrades without a migration thrash.

05b · Speech Services

One STT service every product calls. TTS sits alongside for voice-out.

Speech is its own gateway. Insights ingests recordings in batch (4× real-time). Agent Assist streams partials over WebSocket inside a 2s budget. Conversational AI talks to STT for voice-in and TTS for voice-out inside an 800ms voice budget. All three reach the same service. Centralising here gives the platform per-tenant provider selection, configurable two-layer PII handling, domain vocabulary tailoring, provider-aware reconnection, and a single span per transcript in the trace. The same discipline as the Model Gateway in 05 — a different service because audio is not text and the failure modes are different.

Speech Services · STT main pipeline with two-layer PII; TTS strip for voice-out, same pattern.
PII handling on two layers — provider redaction plus Presidio

Provider redaction (Deepgram redact=numbers&redact=pii, AWS Transcribe Content Redaction) runs in-stream at near-zero added latency and catches structured entities — credit cards, SSNs, account numbers, names, addresses — at transcript time. It is the first line of defence and meets the BRD's "LLM must never receive unmasked PII" requirement on the hot path. Presidio runs as a second pass on the final transcript, with per-tenant rule profile (HIPAA tenant adds DEA + MRN; FCA tenant adds NI numbers; PCI tenant tightens the card pattern). Belt-and-braces. The downstream Model Gateway PII Guard (slide 05, step 2) is a third tripwire that audits the redacted text before it reaches the LLM. Three layers because each catches what the others miss — provider taxonomies vary, Presidio NER drifts, and the gateway audit closes the loop.

Per-tenant tier maps to a PII rule profile, not a per-customer rule list

Standard-tier tenants get the platform's default 12-entity profile (name, address, email, phone, CC, SSN, account, DOB, IP, license, MRN, DEA). Isolated-tier tenants get a per-customer rule pack maintained by their compliance officer through the Tenant Admin Portal — add patterns, change action (mask vs hash vs drop), set per-entity confidence thresholds. Premium-tier tenants get custom NER models trained on tenant samples in Phase 3, sitting in the Presidio NER pass slot. The tier in slide 03 has a real consequence in this layer — it is not just a packaging tier, it determines what compliance posture the platform can credibly claim per tenant.

Domain vocabulary is configurable and auto-mined

Configured: compliance officers and ops managers upload term lists per tenant — Keyterm Prompting on Deepgram Nova-3 (up to 100 terms, ~90% keyword recall rate; pre-Nova-3 falls back to legacy Keywords with boost weights), custom vocabulary tables on AWS Transcribe, phrase hints on Google STT. Auto-mined: a fortnightly job samples low-confidence words across the tenant's transcripts, clusters them, and proposes additions to the Vocabulary Store for human review (accept / reject / edit). Without auto-mining, vocab decays as products and customer language evolve — new SKUs, new regulations, new accents. With it, the WER benchmark in 4.1.2 of the BRD (>92% on tuned model) becomes defensible quarter over quarter, not just at launch.

Reconnection logic is provider-aware and consumer-aware

Streaming (Agent Assist, Conv AI voice). Reconnect Manager keeps a rolling ~30s audio buffer per active stream. On provider disconnect, it attempts session resumption (Deepgram resume token, Google bidirectional reconnect) within the provider's session window; if resumption fails, it opens a new session and replays the buffer to recover the in-flight utterance. Both inbound CCaaS WebSocket and outbound provider WebSocket are pre-warmed at call-connect to eliminate first-byte setup latency. The Agent Assist 5.1 BRD requirement of CCaaS reconnect within 5s falls out of this design. Batch (Insights). Reconnection is a non-issue but partial-job resumption matters — chunked uploads with a manifest, resume from last successful chunk on retry, dead-letter queue after three failed attempts. Configurable per consumer: Agent Assist gets aggressive reconnection (latency-sensitive); Insights gets conservative (cost-sensitive); Conv AI gets a middle policy with barge-in awareness.

Telemetry emitted by default — STT is the platform's eval signal

Every transcript emits an OTel span with tenant ID, provider, language, mode (batch/stream), partial→final lag, audio seconds, redaction counts by entity type, vocab-hit rate, reconnection events, and provider cost. A 0.5% sample is re-transcribed against a frozen golden provider (Whisper-large-v3 self-hosted) for WER drift comparison. The L7 Drift Detector (slide 02) consumes these spans and raises "STT WER on tenant X dropped 3% this week" alerts before a tenant notices. Without telemetry emitted from this layer by default — not as an opt-in — the BRD's "AI–human QA agreement >90%" target is undefendable when QA accuracy regresses, because we will not know whether the cause is upstream STT or downstream LLM.

Why STT is its own service, not a Model Gateway feature.

The Model Gateway in slide 05 was built for request-response calls with a small, well-bounded set of parameters (prompt, model, temperature). STT is a different beast: streaming WebSockets with backpressure, batch jobs that span hours, provider-side configuration that is far richer than an LLM call (vocabulary, redaction taxonomy, language detection, diarisation, custom models), and recovery semantics that have no LLM analogue (session resumption, partial-final reconciliation). Forcing STT through the Model Gateway would either bloat the gateway with audio-only concerns or push those concerns into every consumer service — both worse than a dedicated layer.

Splitting them also clarifies the eval story. Model Gateway evals measure response quality (LLM-as-judge, golden answers). STT evals measure transcript quality (WER, redaction recall). Different golden datasets, different drift signatures, different remediation paths.

What this enables that competitors don't routinely do.

Provider portability without code change. Switch a tenant from Deepgram to AWS Transcribe by flipping the Tenant STT Config — vocabulary translates between Keyterm Prompting and custom vocabulary tables automatically, PII rules translate between provider taxonomies, telemetry stays consistent. Cresta, Observe.AI, and ASAPP's published architectures bind tightly to a single STT provider (mostly Deepgram); switching costs them a code release.

Compliance isolation per tenant. A US healthcare tenant gets HIPAA-tightened PII profile + Whisper self-hosted in a HIPAA cell; the same platform serves a UK retail tenant with FCA wording detection on Deepgram in eu-west. One service, two postures, zero contamination — because the rule profile and the provider selection are both tenant-config, not platform-global.

Vocabulary as a federation candidate. Phase 2 Federation Tier (slide 01 trade-off) can offer anonymised vocabulary contributions across consenting tenants in the same vertical — every healthcare tenant benefits from the union of medical terminology, without exposing any tenant's specifics. STT vocabulary is one of the cleanest federation surfaces because terms are typically not PII.

The single most common WebSocket failure — backend timeout

Every major cloud's L7 load balancer defaults the backend timeout to 30 seconds. For request-response APIs that's fine; for a WebSocket carrying a 5-minute call it is the cause of the disconnect storm you'll spend a week debugging. The fix is one config knob — --timeout=3600 on the backend service (GCP BackendConfig), idle timeout on ALB target groups, or App Gateway listener timeout — but it has to be set explicitly per cell, audited at deploy time, and re-verified after every infra refresh. Pair this with an application-level keepalive ping every 25s on the WS frame layer to detect half-open connections that the LB cannot see. Without both, a quiet 30s pause in audio (customer thinking) drops the call.

Autoscale on active connections, not CPU — and why it matters at peak

WebSocket pods can hold thousands of idle connections at near-zero CPU; CPU-based HPA will under-provision and a sudden burst of speech across all of them will saturate the node before CPU has a chance to spike. Scale on active_websocket_connections exposed by the service as a Prometheus metric, target ~150-200 streams per pod (the sizing rule above), and let KEDA scale on connection-rate as well as count — a deployment serving 200K stable connections is under less load than one churning 20K every 30s. Connection count gates pod count; connection rate gates how aggressively the cluster autoscaler adds nodes. Both metrics, both signals.

Reconnect-resilient state — buffer in managed Redis, not in pod memory

The Reconnect Manager's audio buffer must outlive the pod that received the audio. If the buffer lives in pod memory, a pod evicted for any reason — node patch, OOMKill, deploy roll — drops the in-flight call irrecoverably. Buffer in a managed Redis cluster keyed on {tenant_id}:{call_id}:{epoch_seq}, TTL'd to 60s, replicated across two zones with cluster-mode failover. The service tier itself stays stateless except for the in-flight provider WebSocket, and any pod can pick up any reconnecting client by reading the buffer back from Redis. This is what makes the CCaaS <5s reconnect SLA achievable at p95 rather than just at p50.

Provider connectivity — private links earn back the latency budget

Public-internet hops to a provider add 30-80ms of jitter and an unpredictable failure mode (BGP changes, ISP issues) that does not respect your SLA. Where the provider supports it, run the connection over the cloud's private connectivity service: AWS PrivateLink for Deepgram and AWS-native services, GCP Private Service Connect for Vertex AI Speech and Deepgram-on-GCP, Azure Private Endpoint for Azure Speech. Same-cloud traffic shaves both latency and exit egress cost (the second matters more than people expect at 10K+ calls/day — public-internet egress runs $0.05-0.09/GB; private connect drops it to $0.01-0.02/GB). For providers without private connectivity, pre-warm a pool of HTTP/2 connections with persistent TLS sessions so connection setup doesn't appear in the per-call latency budget.

Why a connector pool, not a unified abstraction

An over-abstracted "CCaaS adapter" interface forces every connector to fit the lowest common denominator and breaks the moment a vendor adds a feature (Genesys Voicestream, Connect Contact Lens). The pool model lets each connector use the richest API that source provides — webhook + CTR for Connect, voicestream for Genesys, manifest for SFTP — while keeping the contract on the output side of the connector uniform: every connector emits the same typed manifest entry plus an audio reference. Internal consumers (Recording Ingest Svc, downstream STT) see one shape; vendor heterogeneity is contained at L1.

QA Scoring Engine — rubric DSL, LangGraph orchestration, calibration loop.

The QA Scoring Engine is the most product-specific service in Insights. The orchestration choice matters because the BRD allows 5–12 parameters per rubric, with weights and pass/fail thresholds, with rubric versioning and historical re-scoring, and with confidence gates that surface low-confidence parameters for human review. A naive implementation — one large prompt that returns a scored rubric in JSON — runs into three problems: parameters interfere with each other (the model defaults to averaging), evidence quotes get dropped to save tokens, and tenant rubric changes require a full prompt rewrite. The architecture below treats each parameter as an independently orchestrated node and the rubric as versioned config, not code.

QA Scoring Orchestrator · LangGraph DAG with parallel parameter nodes, reducer, confidence and persistence gates, and a calibration loop closing back to the compile step.

Rubric DSL — versioned config, not code.

A rubric is a YAML document committed to the L5 Config Service, owned by the tenant's QA Manager, edited through the Tenant Admin Portal's rubric editor, and promoted dev → staging → prod through an approval workflow. Each parameter declares: id, name, scale (binary, 1–5, %), weight, pass_threshold, type (objective / subjective), depends_on (other parameter ids), model_class (Haiku / Sonnet / Opus / tenant-FT), prompt_template, evidence_required, and confidence_floor. The rubric is immutable once promoted — re-scoring history against a prior rubric just reads the prior version_id from the Config Service. Diff-and-approve in the editor surfaces every change a QA Manager makes, with a preview run against a held-out sample before promotion.

This is what makes the BRD's "re-score historical calls against prior rubric versions" requirement (4.2) tractable — the rubric is the orchestration. Replaying a call against rubric v3 means recompiling the v3 DAG and running it; nothing is stored in code paths that need to be unwound.

Calibration loop — the only path to >90% agreement.

Drift Detector consumes the OTel spans the orchestrator emits per node and computes rolling AI–human agreement per parameter on the tenant's calibration set (BRD requirement: ≥100 labelled calls). When agreement drops below the tenant-configured floor (-3% rolling default), the Calibration Svc opens a remediation workflow: (1) sample the disagreements, cluster the pattern, propose a prompt amendment or a new few-shot example, and run a held-out evaluation; (2) if (1) is insufficient and the tenant is Premium, queue a LoRA fine-tune of the parameter's scoring model on the tenant's accepted examples; (3) if (2) is still insufficient, escalate to the QA Manager for rubric-definition review — sometimes the human definition has drifted, not the model.

Each step is a tenant-scoped artifact: a prompt opt is a new prompt version pinned in the Config Service; a fine-tune is a model weight stored in the tenant's cell. Nothing crosses a cell boundary unless the tenant explicitly opted into the Federation Tier (slide 04).

Why LangGraph, not LangChain or a hand-rolled orchestrator

The QA Scoring Engine needs three things from its orchestrator that off-the-shelf options handle differently. (1) Typed nodes with retries and provider fallback. LangGraph nodes accept and emit typed Pydantic objects, retry per-node with policy from the Model Gateway, and recover from a failed parameter without redoing the whole call. LangChain's runnable composition handles retries less precisely. (2) Parallel-where-independent execution with a deterministic reducer. Independent parameters (greeting, close, compliance phrase) run in parallel; dependents wait. LangGraph's graph model expresses this naturally; a hand-rolled async orchestrator can do it but the team will spend two sprints on edge cases. (3) Checkpointing OFF. LangGraph supports persistent checkpointing for long-running agents — Insights explicitly disables it because checkpointed DAG state would land outside the persistence gate. The orchestrator runs in-memory only; if a parameter node fails terminally after retries, the whole call fails into the DLQ and is retried as a unit. Build on LangGraph (Apache 2.0); fork only if the project freezes — at the time of writing it does not.

Per-tenant fine-tuning pipeline — STT vocab, prompt opt, and Premium-tier LoRA.

The BRD calls for "per-enterprise accent fine-tuning capability" on STT (4.1.2) and an active-learning loop on QA scoring (4.2). The fine-tuning pipeline below operates at three intensities depending on what tier the tenant is on, what their data volume supports, and what they've explicitly opted into.

STT vocabulary tier (all tenants).

The auto-mining job declared in slide 05b samples low-confidence words across a tenant's transcripts fortnightly, clusters them, and proposes additions to the Vocabulary Store. Compliance officers and ops managers accept / reject / edit through the Tenant Admin Portal. Vocabulary terms feed Deepgram Keyterm Prompting, AWS Transcribe Custom Vocabulary, and Google Speech phrase hints. No model weights change; only the per-tenant vocab set. Available to all tenants, no opt-in beyond joining the platform.

Prompt-opt tier (Standard / Isolated, opt-in).

For QA scoring, prompt optimisation runs on the tenant's calibration set: the Calibration Svc proposes new few-shot exemplars from accepted human reviews, runs a held-out eval against a frozen golden set, and promotes the new prompt version to the Config Service if eval improves with no regression. DSPy or a lighter custom optimiser drives the search. No model weights change; only the per-tenant prompt version. Requires the tenant to opt into transcript + calibration retention (otherwise there's nothing to optimise from).

LoRA tier (Premium, opt-in).

Premium tenants with ≥1000 calibrated samples can request a LoRA fine-tune of either (a) a small scoring SLM for a specific subjective parameter (empathy, professionalism), or (b) a custom acoustic STT model for accent / vertical vocabulary. Training runs in a tenant-dedicated GPU node pool inside the tenant's cell; samples and resulting weights never leave the cell. Models are versioned and pinned in the Config Service alongside prompt versions. Deletion-on-DSR of the underlying training data triggers a retrain workflow if the tenant elects to keep the model in service.

Sentiment + Compliance — same transcript, two parallel consumers.

Sentiment Analyser — ties back to the L2 sentiment stream.

Insights does not run its own sentiment model. The L2 Sentiment Stream — declared in slide 02 and called out in slide 05b — produces per-utterance sentiment with confidence at <200ms / utterance. The Insights Sentiment Aggregator consumes that stream off Kafka and rolls it up four ways: per-call (positive / neutral / negative + confidence), per-segment (opening / problem / resolution / close from the segment classifier), escalation-risk score (a small classifier over the timeline shape), and per-agent / per-queue / per-time trend (ClickHouse pre-aggregation). Sentiment timeline is persisted only if the tenant has opted into transcript retention; otherwise the rolled-up scalar persists with the QA score and the timeline is discarded.

The Aggregator is also the consumer that subscribes the supervisor live view (built once for Agent Assist in slide 07; reused here for Insights coaching).

Compliance Detector — trigger library + LLM hybrid.

The Compliance Detector is a hybrid because each technique alone fails. Pure regex misses paraphrase ("we may record this call" instead of "this call may be recorded"); pure LLM hallucinates compliance achievement when the agent skipped the wording. The implementation: a per-tenant Trigger Library in Postgres lists rules with literal phrase, regex variant, severity (critical / warning / informational), and an LLM verification prompt; the detector first scans the transcript for any literal or regex hit, and only on a hit does it call the LLM via the Model Gateway to confirm the disclosure intent was met. False-positive suppression is the LLM's job; false-negative recall is the regex's job.

Self-service flag library management (BRD 4.5) is the Compliance Officer Console — add rules through a guarded form, run a validation job against a 100-call sample, see pass/fail/borderline counts, promote to prod via an approval workflow. Rules in staging mode emit telemetry but do not block any QA pass/fail decision; rules in prod mode can mark a call non-compliant even if QA scoring passed.

Coaching workflow + dashboard mini-SaaS.

The Coaching Workflow Svc is what most BPO managers will see day-to-day. Calls below the tenant-configured QA threshold auto-populate a per-manager queue, sorted by score gap × call recency × agent priority. The manager opens a queued call: redacted transcript on the left, AI-scored rubric overlay on the right with the evidence quote per parameter, sentiment timeline beneath, compliance flags inline. The manager leaves structured feedback (a comment + an action — practice script, retraining session, escalate, no-action), signs off, and assigns a follow-up. The calibration paradox — accurate AI requires retained data

The pure ZDR path (no transcript persistence) returns a score and discards the transcript. It cannot, by definition, support calibration: a reviewer cannot agree or disagree with a score they cannot read evidence for. This is not a hidden cost — it is a stated tier choice in the contract. The slide 04 Federation Tier resolves this for tenants who want the platform-wide model to improve from their data; tenants who do not federate still benefit from their own calibration loop inside their own cell.

The two NFRs that genuinely depend on tenant cooperation

The architecture earns most BRD targets unilaterally — failover, latency, scale, retention, isolation, drift detection, audit. Two NFRs are different because their accuracy floor is set by tenant data, not by the platform: (1) AI–human QA agreement >90% requires a calibration set of ≥100 labelled calls per tenant per rubric version (BRD §4.2), and the calibration paradox above means the tenant must opt in to redacted-transcript retention to support reviewer agreement. (2) WER >92% on tuned model requires the tenant's vocabulary list to be populated either manually (compliance officer uploads) or via the auto-mining job once enough transcripts have accumulated. Both targets are reachable in 4–6 weeks per tenant, not on day 1 — the proposal should not pretend otherwise. The drift detector and the calibration UI exist precisely to make the path to target visible to the tenant rather than asking them to take it on faith.

The cold-start tradeoff — KEDA scale-to-zero vs the 5-min SLA

KEDA scale-to-zero is the right default for cost on idle queues, but a cold scale-up costs 30–60s of pod-and-image fetch time. For a tenant with sparse, time-sensitive recordings (e.g., post-call near-real-time mode), scale-to-zero risks pushing the 5-minute QA SLA into the cold-start window. The mitigation is per-tenant lane policy: Standard tenants on hourly-batch ingest scale to zero (cost-optimised); tenants on near-real-time ingest run with a scale-floor ≥1 pod plus a warm node pool with pre-pulled container images. The tenant chooses lane behaviour via Tenant Admin Portal; the platform tracks the cost / SLA tradeoff per tenant and surfaces it in the cost dashboard.

The 90% AI-human agreement bar is the hardest target in this product

Achievable on objective rubric items (greeting present, compliance phrase said, call recorded). Difficult on subjective items (empathy, professionalism). Realistic plan: launch with rubrics that are 70% objective + 30% subjective, hit 90%+ on objective and 80%+ on subjective in v1, iterate subjective with calibration-loop fine-tuning over months. Premium tenants who reach ≥1000 calibrated samples and opt into LoRA fine-tune typically close the subjective gap by quarter two. Confidence: moderate on hitting 90% across all parameters within 6 months of launch per tenant.

Re-scoring history — rubric versions are immutable, not mutable

The BRD requires the ability to re-score historical calls against prior rubric versions (4.2). The architecture supports this because rubrics are immutable in the Config Service: every promotion creates a new version_id, prior versions remain readable, and the QA Scoring Orchestrator can compile any historical version on demand. The Re-Score Job Runner queues a re-score against a version_id + tenant time window; results land in a separate Postgres table keyed on (call_id, rubric_version_id) so historical and current scores coexist. Cost gate: re-scoring is a tenant-billable operation (it's another full DAG run per call) and requires retained transcripts — same calibration-paradox constraint as live calibration.

Why this architecture hits 2s p90 — honestly.

The clock starts at the customer's end-of-speech and ends when a suggestion is fully rendered and confidence-gated. The architecture is a streaming pipeline, not a batch one — STT emits partials from ~150ms in, sentiment and PII run on partials, the LLM may even be invoked on the latest partial with a "reflow" if the final transcript differs. Final transcript arrives ~80ms after end-of-speech for streaming Deepgram (per Nova-3 published numbers).

The dominant latency is the LLM streaming call. Anthropic Claude Haiku 4.5 hits first-token ~0.71s and a full short-form suggestion (~50–80 tokens) at ~1700ms. Add ~50ms for confidence gating and render — total ~1750ms p90. Frontier models (Sonnet 4.6 at ~1.25s TTFT, GPT-class similar) push first-token past 800–1000ms and full suggestion to 2.5s+, which is over budget. Architecture defaults to SLM for Agent Assist via a tenant flag in the Model Gateway tenant config; Sonnet is opt-in for moment-types where quality dominates latency (sensitive empathy, regulatory wording).

Moment detection is the real problem, not latency.

Even if the suggestion arrives at 1700ms, it's useless unless it appears at the right moment. Most agent calls have only 5–10 moments where a suggestion is welcome (compliance reminder due, customer expressing frustration, knowledge gap detected). Continuous streaming suggestions are noisy and get ignored by agents within days.

The Trigger Detector at L2 runs a small classifier (10–30ms) on every partial: is this a moment that warrants a suggestion? 80%+ of stream windows produce no suggestion. This both cuts cost (fewer LLM calls) and improves agent adoption (less noise). The BRD does not specify this; it is the most important UX decision in the product, and it lives at L2 — before the orchestrator — so the cost saving compounds with cache and SLM routing downstream.

Suggestion Orchestrator — LangGraph on the partial transcript.

The Suggestion Orchestrator is a LangGraph DAG that runs per detected moment (not per partial — only when the Trigger Detector fires). The DAG has four parallel-where-independent reasoning nodes plus a reducer; each calls the Model Gateway, never a provider directly. Per slide 05's pipeline, every call passes through tenant context → PII Guard tripwire → quota → SLM router → cache → provider — there is no path that bypasses the gateway. PII redaction is two-layered before the gateway (provider redaction in stream + Presidio NER on the partial as the transcript leaves L2) and the gateway PII Guard is a third tripwire that audits the redacted text before the LLM ever sees it. The LLM never receives unmasked PII (BRD §5.6, §7.2).

The four parallel nodes.

Next-Best-Action node — given current transcript window, sentiment, topic, and CRM context, produces a recommended action ("offer 30-day extension," "schedule callback for tier-2"). Streams from Haiku 4.5 by default; gated on confidence floor configured per moment-type. Compliance node — grounded on the per-tenant flag library (slide 06's compliance pattern reused) and current moment; outputs either a remind-prompt ("recording disclosure not yet stated") or null if no flag fires. Empathy node — consumes the L2 sentiment timeline and the customer-tone classifier; outputs an empathy nudge ("acknowledge frustration before next answer") only when the tone delta crosses a configured threshold. Knowledge node — calls RAG against the per-tenant Knowledge collection; if top-k rerank score clears the floor, returns a cited answer to surface in the overlay. The four nodes run in parallel on the partial; a deterministic reducer aggregates into a single SuggestionPacket (Pydantic) with confidence, source, and citation.

Why LangGraph here, and why checkpointing is OFF.

The same three reasons LangGraph won for Insights' QA Scoring Orchestrator (slide 06) hold here: typed nodes with retry and provider fallback, parallel-where-independent execution with a deterministic reducer, and an explicit checkpointing toggle. Checkpointing is OFF for Agent Assist — checkpointed DAG state would land outside the persistence gate and break ZDR. The orchestrator runs in-memory only; if any single node fails terminally after retries, the reducer drops it and the rest of the suggestion still arrives (degraded but useful). LangGraph parallel-fan-out benchmarks (sequential→parallel speedup, max_concurrency cap, 5–15ms checkpoint overhead when ON / zero when OFF) were the call-out for slide 06 and apply identically here. max_concurrency is set so per-tenant rate limits at the gateway are never breached even on a moment burst.

CRM integration — pull at connect, push after summary, HITL on writes.

CRM is two distinct flows on opposite ends of the call. Both go through the L1 CRM Adapter pool (per-CRM authentication, per-tenant field map versioned in Config Service) and use the same OAuth/SSO model the platform's IdP broker manages. Per-tenant rate-limit awareness is built in — Salesforce's API governor limits and Zendesk's request budget are platform-tracked, with backoff and warning surfaced to the Tenant Admin Portal so a tenant nearing their CRM quota sees it before a real call fails.

Pull at call connect — <500ms p95.

The Streaming Adapter receives the call-init event from CCaaS (Genesys conversationStart, Connect ContactInitiated, Twilio call.initiated) before the agent's screen finishes rendering. It triggers the CRM Context Svc with the inbound caller identifier (ANI / DNIS / external_id from the IVR). The Context Svc runs a single SOQL or REST query against the configured CRM, with per-tenant field projection (Account, Contact, last 5 cases, open tickets, LTV, account tier, NPS) and returns within 350–450ms p95 — well inside the 500ms BRD target. By the time the agent's overlay renders, the customer card is hydrated. Phase 1 = SFDC Service Cloud + Zendesk; Phase 2 = ServiceNow + HubSpot; Phase 3 = mobile SDK + custom REST. SOQL response is cached at the CRM Context Svc with a short TTL (≤30s) keyed on caller_id so a re-render within the same call doesn't double-hit SFDC.

Push after summary — HITL by default, auto in Phase 3.

On call end, the Post-Call Summariser produces a CallSummary object: free-form summary (≤300 chars), mandatory outcome / RCA code (BRD §5.2.3, drawn from the tenant's outcome taxonomy in Config Service), and CRM-field draft (case Description, Status, Resolution, Reason, custom fields). The summary is written to the L4 Post-Call Summary Store (S3 + CMK + Postgres meta if the tenant opted into retention, otherwise discarded after the agent dismisses it). The agent reviews in the overlay's post-call panel: edit-in-place, then one-click save writes through the CRM Adapter (Phase 1 default). For Premium tenants in Phase 3, an auto-save lane writes when summary confidence clears the configured floor and a per-tenant audit row records the auto-write — HITL is the default; auto-write is an opt-in per moment-type. Failed CRM writes land in a per-tenant DLQ and surface as a notification in the agent overlay; no silent drops.

Tenant-scoped Knowledge RAG — per-tenant collection, ACL preserved, hybrid retrieve.

The BRD §5.4 specifies tenant-scoped vector store with no cross-customer retrieval, hybrid retrieval, P95 < 500ms, and >88% retrieval accuracy. The Knowledge RAG service implements all four against the platform spine's RAG service (slide 02 / slide 06's pattern), with one Agent-Assist-specific add: the retriever runs during the suggestion DAG, not at ingestion. Ingestion is a different pipeline.

Ingestion (offline).

The Tenant Admin Portal's KB ingestion UI accepts PDFs, DOCXs, URLs (web crawl), Confluence / SharePoint / Drive (connector OAuth). Each document is chunked (configurable chunk size + overlap), embedded with Voyage voyage-3 through the Model Gateway's embeddings lane, and written to a per-tenant Qdrant collection. Chunks preserve source ACL metadata — Confluence space restrictions, SharePoint site permissions — so retrieval can filter on the agent's per-call entitlements. Ingestion runs in the per-tenant cell only; no document leaves the tenant boundary. Cross-customer retrieval is impossible because the Qdrant client is constructed per-request with the tenant's collection ID, attached by the Tenant Router at ingress.

Retrieval (online, hot path).

The Knowledge node in the orchestrator emits a query against the live transcript window. Hybrid retrieval = dense (Voyage) + sparse (BM25 on OpenSearch) with configurable weighting per tenant. Top-50 candidates from each go through Cohere Rerank for ~15–20pp lift on retrieval accuracy at marginal cost vs an LLM call. P95 retrieval lands at 200–300ms (vendor benchmarks), well inside the 500ms BRD floor. Citation metadata (doc title, section, URL) accompanies the chunk so the agent overlay shows "Source: KB §4.2" — clickable to the original doc, audit-able by Compliance.

ZDR posture for KB.

The Knowledge Vector Store is the one L6 store that is always-on for Agent Assist tenants, because tenant-owned KB documents are not call-data — they are config, owned by the tenant, ingested with explicit consent, and retrieved (not generated) on the hot path. ZDR applies to the call payload; the call payload is never persisted to the KB. The KB encrypts at rest with per-tenant CMK; deletes on document removal trigger a chunk-level vector delete plus an audit row through the persistence gate's audit channel, the same channel slide 04b uses for DSR fan-out.

Post-Call Summariser & PII removal — gateway-mediated, cache-friendly.

Post-call is a second LangGraph DAG (smaller than Suggestion: Summariser → RCA Classifier → CRM-Field Drafter → Confidence Reducer) that runs after CCaaS emits callEnd. Input is the full redacted transcript (the same two-layer-PII output the live pipeline produced — provider redaction in stream + Presidio second pass) plus the CRM context already loaded for the call. Each node calls the Model Gateway; PII removal happens at the Speech Services boundary (slide 05b, two layers) before the transcript ever reaches the gateway, and the gateway's own PII Guard (slide 05, step 2) is the third tripwire that audits the text immediately before LLM dispatch. By the time the summariser node receives the transcript, names / phone numbers / card data / account numbers / health identifiers are masked per the tenant's rule profile — the LLM literally cannot see unmasked PII because the gateway rejects payloads that fail the tripwire scan.

Anthropic prompt caching cuts 85% latency / 90% input-cost on the cached prefix — for the summariser, the prefix is the rubric / outcome taxonomy / RCA code list, which is identical across calls for a given tenant. Realistic numbers: median summariser DAG runtime ~6–9s, p95 ~14s, with the agent reviewing in the overlay while the summary streams in. The summariser is async — the agent does not wait synchronously on call-end; the panel updates as tokens arrive.

Agent Desktop Overlay — embeddable Web Component, cross-host.

The overlay is built as a Lit Web Component (BRD §5.5: Salesforce Service Cloud, Genesys Desktop, custom UIs). Lit is chosen over a React-only build because Salesforce LWC, Genesys's Aura wrapper, and the long tail of "custom UIs" (Twilio Flex panels, Connect CCP overlays, in-house Java desktops) accept Web Components everywhere they accept anything; a React-only widget needs a React shell or an iFrame in each host. The overlay component has four panels (BRD §5.5): live suggestions stream (subscribes to Live Suggestion Svc WebSocket fan-out), CRM context card (hydrated by CRM Context Svc on call-init), knowledge search (manual lookup against the same tenant Knowledge RAG, with the same citation surface as auto-suggestions), and post-call summary (review + edit + save). Layout is tenant-configurable — the Tenant Admin Portal panel-layout editor outputs a layout JSON pinned in Config Service; the overlay loads its own tenant's layout at boot. Per-customer branding (colour, logo, font) is the same Config-Service-driven model the rest of the platform uses.

Auth is SSO-stitched: the agent's host application (SFDC, Genesys) is already SSO'd to the customer IdP; the overlay receives a short-lived JWT for the platform via the L5 IdP Broker, and the WebSocket carries that JWT. The overlay never holds long-lived credentials. Network egress is minimised — the overlay talks to a single platform endpoint (the per-cell Live Suggestion API), so customer firewalls only need one allowlist entry.

Feedback loop — every thumb closes back to L7 and (opt-in) federation.

Every suggestion the overlay renders carries a thumbs / why-control. Agent input writes to the Feedback Service: {tenant_id, agent_id, call_id, moment_id, suggestion_id, rating, reason_code, free_text_redacted}. The Feedback Svc emits an OTel span to the L7 stack and a row to the Feedback Store (Postgres, RLS, 12mo TTL default). The same span schema feeds Langfuse for trace replay during incident review, and feeds the Drift Detector for rolling helpful% per moment-type / per agent / per rubric — the same drift-loop pattern slide 06 uses for QA agreement.

Drift signal triggers the Calibration Svc to (a) propose a prompt amendment for the affected moment-type, (b) for Premium tenants, queue a LoRA fine-tune of the Suggestion Orchestrator's relevant node on the tenant's accepted thumbs-up examples. Both artefacts are tenant-scoped and stay inside the tenant's cell; Federation is the only path that aggregates across tenants.

Per slide 04, the Federation Tier is opt-in per tenant. Tenants who opt in run a Federation Sidecar in their cell that anonymises and DP-protects (k-anonymity k≥20, ε≤1.0) outgoing signals before they reach the platform-owned Aggregator. The Aggregator never sees raw transcripts or PII; it sees moment-type signals and outcome deltas. This is what makes the BRD's "automated retraining trigger" (§5.6) compatible with ZDR-default — federated tenants contribute, the platform learns the rising tide, and non-federated tenants benefit only inside their own cell. Realistic adoption: ~20% of tenants in year 1, growing as the value-share meter shows the commercial credit federating earns.

The agent's free-text reason is redacted through the same Presidio rule profile before it ever leaves the cell — the loop closes without leaking the customer's identifying data.

Low-confidence handling — three behaviours, configurable per moment

STT confidence is a per-word value. When confidence is low (noisy audio, accent the model wasn't tuned for, overlapping speech), the platform has three behaviours: (a) suppress the suggestion and wait for a clearer transcript; (b) emit with confidence indicator on the agent UI; (c) fall back to a non-LLM rule-based suggestion (e.g. compliance prompt that doesn't require understanding the customer). The architecture supports all three, configurable per tenant per moment-type. Default behaviour: suppress the first low-confidence partial; emit with indicator if confidence stays low for >1s. Confidence: moderate · this is product judgment, not architectural fact, and the right defaults will move with rollout data.

CRM write-back rate limits — the silent failure mode at scale

Salesforce's API governor limits (24h rolling window, per-org), Zendesk's request budget, and ServiceNow's rate caps are real bottlenecks at high tenant volume — a 5,000-agent BPO running 250K calls/day cannot saturate SFDC's standard tier. The CRM Adapter pool tracks per-tenant rate-limit consumption and surfaces it in the Tenant Admin Portal cost dashboard (alongside LLM token spend). Premium tenants get priority queuing and a backoff that retries auto-saves but never one-click saves (HITL writes are user-initiated; they get the next available slot). Per-tenant pre-flight check at onboarding ensures the SFDC package is configured for higher limits before the first production call.

Agent Runtime — LangGraph as the compiled execution layer.

The Agent Runtime is the L3 service that compiles a tenant's published flow JSON into a LangGraph DAG and executes it per turn. It is the place where typed-node retries, parallel tool-use, streaming token responses, and the in-memory-only / Postgres-checkpointed switch get decided. LangGraph is chosen for the same three reasons the Insights QA Orchestrator (slide 06) and Agent Assist Suggestion Orchestrator (slide 07) chose it — typed nodes with retry and provider fallback, parallel-where-independent execution with deterministic reducers, and an explicit checkpointing toggle that lets the platform run ZDR-strict by default and retained-state on tenant opt-in. LangGraph v1.1's middleware layer adds model-retry-with-backoff and content-moderation middleware out of the box; we wire our PII tripwire and Guardrails as middleware so the runtime path is consistent across every tenant.

Three operating modes, one runtime.

ZDR-strict (default). Checkpointing OFF. The DAG runs in-memory only; session state lives in Redis with TTL ≤600s; no AOF / no RDB; nothing persists. Suitable for Standard-tier tenants and any tenant without explicit retention opt-in. Cost: full state reconstruction on reconnect requires re-walking the channel adapter's message buffer (≤30s window, managed Redis).

Retained (opt-in). LangGraph PostgresSaver writes checkpoints to the tenant's Postgres schema with RLS, configurable TTL (default 30d), audit row through the Persistence Gate per checkpoint write. Suitable for tenants where conversation continuity across sessions matters (account-tied banking flows, support cases that span days). Latency overhead: 5–15ms per node when ON.

Premium dedicated. Dedicated Postgres in the tenant's cell, BYOK / BYOC. Same PostgresSaver path; the only difference is the storage backend and key custody.

Why this matters — failure modes LangGraph closes.

Independent industry data finds over 60% of agent production incidents trace to state management. The runtime closes the three sub-modes most often: (1) session pollution — state leaking across turns or tenants — closed by tenant-scoped thread_id and RLS on the saver; (2) partial failure on tool call — closed by middleware retry + per-tool timeout + the reducer pattern that lets one node fail without dropping the whole turn; (3) checkpoint disagreement on replay — closed by version-pinned flow JSON so the same conversation always replays against the same DAG. The runtime emits an OTel span per node (tenant_id, flow_version, node_id, model, tool_calls, cache_hit, latency_ms, cost_usd) feeding Langfuse and the L7 Drift Detector.

Provider rate-limit awareness: max_concurrency caps fan-out so a moment-burst (group customer event, viral incident) cannot breach the tenant's gateway quota even under load. The parallel fan-out itself benchmarks at large speedups vs sequential — the gateway aggregator and the deterministic reducer mean a 4-tool turn completes in roughly the time of the slowest call, not the sum.

Voice flows that need a tool call need a filler — built into the runtime, not the flow

The 800ms p95 voice budget is achievable on simple turns (greeting, disambiguation, KB-grounded answers) but not on turns that require a synchronous tool call (account lookup, payment authorisation, address verification). The Agent Runtime handles this with a filler-while-tool-runs middleware: when the DAG schedules a tool call whose estimated latency exceeds 600ms, the runtime emits a conversational filler ("let me look that up for you") through TTS while the tool runs in parallel. The filler is configurable per agent (style, voice, length) and is a runtime concern, not a flow-author concern — the Builder UI does not expose a "filler" node because it's the wrong abstraction; the runtime always knows whether a filler is needed based on tool-latency telemetry.

Why the canvas / runtime split is the right seam.

The Builder produces a serialised flow graph; the Runtime executes it. The two communicate through one contract — flow JSON. This is the seam Cognigy spent five years getting right and the seam most copy-the-OSS-tool projects get wrong. Three properties fall out: (i) the Builder can ship features without runtime risk — a new node type is a node-library change plus a runtime compiler entry; (ii) the Runtime can change implementation (LangGraph version bump, alternative state store) without the Builder noticing; (iii) licensing a different runtime later is a runtime-compiler swap, not a Builder rewrite — if a future commercial runtime offers meaningfully better latency, the cost to switch is the cost to author one compiler, not the cost to rebuild the Builder UI. The flow JSON contract is the only thing that has to stay stable. Confidence: high on the canvas/runtime split being the right architectural boundary; Confidence: moderate on the timeline — 8–12 person-months for v1 No-Code Builder, ~14–20 person-months to feature parity with Cognigy's authoring surface.

Tenant Admin Portal accepts PDF, DOCX, TXT, URL crawl, FAQ, Confluence / SharePoint / Drive (BRD §6.6). Chunked (configurable size + overlap, with chunking preview in the Builder per BRD §6.3), embedded via Voyage voyage-3 through the Model Gateway's embeddings lane, written to the tenant's Qdrant collection. ACL metadata preserved per chunk so retrieval can filter on the bot's per-conversation entitlements (e.g. a self-service bot retrieves only customer-facing KB, not internal procedure docs). Ingestion runs in the tenant's cell only; no document leaves the tenant boundary. Same KB Connector Pool, same ingestion pipeline, same chunk schema as Agent Assist.

Retrieval (online, hot path).

The Knowledge node in the Agent Runtime emits a query against the current conversation window. Hybrid retrieval = dense (Voyage) + sparse (BM25 on OpenSearch) with configurable weighting per tenant. Top-50 candidates from each go through Cohere Rerank for ~15–20pp lift on accuracy. P95 retrieval lands at 200–300ms (vendor benchmarks), inside the 500ms floor with margin to spare. Cross-tenant retrieval is structurally impossible — the Qdrant client is constructed per-request with the tenant_id-keyed collection ID the Tenant Router attaches at ingress; payload filter on tenant_id is a second tripwire (LlamaIndex / Qdrant multi-tenant best practice). Citation metadata flows back to the response so the bot can attribute or the agent reviewing replay can audit.

ZDR posture & KB management.

Knowledge Vector Store is the always-on L6 store — tenant-owned KB documents are configuration, not call data, ingested with explicit consent, retrieved (not generated) on the hot path. ZDR-default policy applies to the conversation payload; the conversation payload is never persisted to the KB. KB CRUD operations (BRD §6.6 add / update / delete, version history, ingestion status) all cross the Persistence Gate with audit rows; document deletion fans out to chunk-level vector deletion plus audit row (the DSR fan-out reused from slide 04b). Encryption at rest with per-tenant CMK; Premium tier on dedicated KMS key policy.

The two NFRs that genuinely depend on tenant cooperation

The architecture earns most BRD targets unilaterally — latency, isolation, retention, observability, portability, residency. Two are different: (1) Goal completion rate depends on flow quality (the tenant's no-code authoring) and KB completeness (the tenant's ingestion discipline). Excellent platform, poorly authored flow, no measurable goal completion — the platform's eval framework makes the gap visible (Promptfoo + DeepEval + Conv AI Eval Sim Harness) but cannot ghost-write the flow. (2) Cost per conversation on agentic / long-tool-chain turns depends on how many turns the bot takes to resolve — a Builder who chains five tool calls per turn will overspend regardless of model. The platform exposes per-conversation cost telemetry to the Builder during simulation so the trade-off is visible at edit time, not at month-end billing.

Why the runtime stays replaceable even though we build it

The Builder produces a flow JSON; the Runtime executes it. The contract between them — flow JSON schema — is the only thing the platform commits to. If a future commercial runtime (Cognigy NICE-retained, Sierra, or whatever post-IPO consolidation produces) offers meaningfully lower latency or richer evaluation, the switching cost is a runtime-compiler swap: a service that reads the same flow JSON and emits the new runtime's native flow representation. Channel Manager, Builder, RAG, Model Gateway, Eval, Guardrails — all reused. This is the same replaceability seam called out in the prior v1 slide; the difference is now we are explicit that we build the runtime first because the seam exists, not because building is strategically right and licensing strategically wrong.

Backend timeout — the silent killer (reused warning from slides 05b and 07)

Every major cloud LB defaults to 30s backend timeout; that is the root cause of the disconnect storm any team building a WebSocket platform will spend a week debugging. Set --timeout=3600 (or equivalent) for the Channel Manager, the Voice Channel Adapter, and the Web Chat WSS endpoint; audit at deploy; re-verify after every infra refresh. Pair with app-level keepalive ping every 25s on the WS frame layer to detect half-open connections the LB cannot see. Voice and chat sessions can run 30+ minutes; an LB that disconnects at 30s drops every long conversation. The warning was cited in slide 05b and slide 07 and applies identically to every L1 Channel Adapter in this slide.

DSR fan-out reuses slide 04b — Conv AI adds three stores

The DSR pipeline in slide 04b enumerated seven stores; Conv AI adds three to the fan-out: Conversation State store (delete by end_customer_id via conv_id mapping), Eval / Trace Store (delete by end_customer_id via conv_id), KB Vector Store (delete by document_id when the customer's KB references the deleted person — same pattern as Agent Assist). Plus Federation Signals: even though signals are k-anonymised, the tenant can request their tenant's federation contribution withdrawn; the Aggregator removes the tenant-batch on the next aggregation window with an audit row.

Backup strategy, by data class.

Aurora (RDS): Continuous point-in-time recovery via S3, retention 30 days; daily automated snapshots, retention 90 days; cross-region snapshot copies for Premium tier.

S3 (transcripts, KB, recordings): Versioning enabled; cross-region replication for Premium tier; S3 Object Lock for audit log buckets (compliance hold, immutable for retention period).

DynamoDB: Point-in-time recovery enabled (35-day window); on-demand backups before major changes.

Qdrant: Snapshot to S3 daily; for Premium tier, hourly. Vector data is reconstructable from source documents in S3, so backup priority is lower.

Kafka (MSK): Retention 7 days for events; replicated within cluster. Lost events are replayable from source systems (recordings, webhooks).

Configuration (GitOps): Git is the source of truth, replicated via standard git mirroring. Cell can be rebuilt from a clean Terraform state + git config.

DR drill cadence.

The platform conducts quarterly DR drills. Each drill exercises one failure scenario from the table above with a randomly selected non-production cell, verified by a runbook, with timing recorded and published to a tenant-visible dashboard.

Premium tenants can request tenant-specific DR drills 2×/year as part of their contract. The platform fails their dedicated cell, recovers within RTO, and produces a signed attestation document the tenant can use for their own SOC 2 / ISO 27001 audits.

Drill failures count. If a quarterly drill misses the RTO target by >25%, the cell is flagged for engineering remediation and Premium tenants are offered service credits per their contract.

Chaos engineering — automated, non-drill — runs continuously in pre-production cells using a fork of Chaos Mesh, exercising pod kills, network partitions, and DNS failures.

Why DR is here and not in observability

DR is a topology and contractual concern, not just an ops practice. It belongs alongside cell architecture and tenancy because it dictates how tenants are placed (cross-region pairs for Premium), how data is replicated (sync vs async, regional vs global), and how the audit log is preserved through cell death. The observability stack detects failures; the DR posture recovers from them. Different concerns, different sections.
