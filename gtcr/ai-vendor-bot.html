02  /  The pitfalls

Technical approach suggested in the PRD — and its pitfalls

Email in, Claude parses it, write to Salesforce. About 200 lines. It genuinely works — it's what we built for the demo. Here is what it can't do, in the order you'd hit it.

1  A failure just vanishes

Salesforce is slow, the function times out, the message is gone. Nobody finds out. The person who sent it assumes it worked.

needs a queue, retries, and a place failed messages land

2  Retrying makes duplicates

Retry the same email and you get two records. Salesforce has no undo and no built-in way to say "this is the same message."

needs one stable ID per message, and upsert instead of create

3  It guesses, and sounds sure

Two people named Aaron. Two vendors starting with "Oli". A function picks one and moves on. Nobody sees that it was a coin flip.

needs name matching, a confidence check, and a review queue

4  Nobody can check its work

Three weeks later a partner asks "why does this record say that?" There is no trace, no original message, no record of which prompt wrote it.

needs provenance stamped on every record

5  A bad day can't be cleaned up

One prompt tweak writes 60 wrong records over an afternoon. Which 60? There's no way to ask.

needs a log tying every record to the version that wrote it

6  The inbox is an open door

Anyone can email the address. A vendor's own words get forwarded straight into a prompt that has write access to your CRM.

needs trust levels, and limits on what each level can touch

7  Salesforce changes underneath you

Someone adds a picklist value. The hardcoded list in the function doesn't know. Writes start failing, quietly.

needs the schema read live from Salesforce, not copied

8  You can never change the model

A better Claude ships. Is it better for you? The only way to find out is to put it in production and watch.

needs a set of real examples with known right answers
AND THEN You do all eight again for Slack. Then chat. Then the mobile form. Four copies that each drift at their own pace.
03  /  The alternative

Our pitch: a mini self-hosted platform

Same components either way, and it all runs inside GTCR’s own cloud. The difference is that the hard parts are built once, behind a contract, instead of copy-pasted into every channel.

FOUR FUNCTIONS — EVERY CHANNEL REBUILDS EVERYTHING
Four copies of parsing, matching, validation and writing. A fix has to land four times, or it isn't fixed.
→
ONE PLATFORM — THIN DOORS, ONE BRAIN
Each channel is a thin adapter. Everything risky happens once, in one place, versioned and watched.
01

A new channel takes a day

Slack becomes an adapter, not a rebuild, because matching and validation already exist.

02

Every record traces back

To the original message, the prompt version, and the model that wrote it. In one click.

03

Model upgrades get tested

Four minutes against 150 real examples with known answers — instead of a leap of faith.

04

Mistakes are findable

And reversible. "Everything written by prompt v13 on Tuesday" is a query, not an archaeology project.

05

One place to change a rule

A new picklist value, a new validation rule, a new required field. Changed once, live everywhere.

06

You can see what it costs

Per message, per channel, per person — so the cost conversation is a number, not a guess.
