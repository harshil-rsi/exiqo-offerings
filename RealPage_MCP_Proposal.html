Slide 3 · Findings

Are these MCP servers available out of the box?

Surveyed: official MCP catalogs, vendor docs, community marketplaces. Only one of the three has a GA-track managed offering.

Oracle Fusion
No official MCP

Oracle has shipped MCPs for Database, MySQL/HeatWave, OCI APIs — not Fusion ERP/SCM/HCM. Roadmap exists; no GA.

Action: Custom build over Fusion REST V1, OAuth 2.0/JWT via OCI IAM domain.
Coupa
No official MCP

Third-party wrappers exist (Composio, PulseMCP, Workato) — none enterprise-grade.

Action: Custom MCP over Coupa Core API. OAuth 2.0/OIDC mandatory; SAML 2.0 SSO at IdP.
BigQuery
Managed MCP available

Google's fully-managed remote BigQuery MCP (Preview, Jan 2026). Schema awareness, query exec, AI.FORECAST.

Action: Consume managed MCP, fronted by a thin proxy adding semantic catalog + audit overlay.
Bottom line: Of the three, only BigQuery is "ready". Oracle Fusion and Coupa MCPs require a careful custom build, with auth and RBAC modeled on each system's existing security plane.

Slide 7 · BigQuery · Semantic Catalog

From business intent to correct SQL — on the first try

A lightweight semantic layer that sits in front of BigQuery, translating natural-language business terms into precise schema, joins, and metric definitions before the LLM ever writes SQL.

Architecture · semantic layer in the request path

Why bother?

  • Accuracy. LLMs hallucinate column names; the catalog maps "MRR" to the exact column + filter your finance team uses.
  • Governance. Metric definitions are versioned and curated, not crowdsourced from prompts.
  • Cost. Validated joins prevent runaway BQ scans (the catalog can warn before SELECT * on a 12 TB table).
  • Onboarding. New agents and analysts get the same definitions — single source of truth.
Build approach
  • Backed by Postgres (RDS) + pgvector for embedding search
  • YAML-based metric definitions, version-controlled
  • Bootstrap from INFORMATION_SCHEMA + LLM-suggested term mapping
  • Curation UI for data team (post-engagement, optional Phase-2)
Effort
~1 person-week within the existing 8-week scope; covered in BigQuery workstream.

Slide 9 · Authentication & SSO · two modes

If a central IdP exists — we federate. If not — we inherit each system's native auth.

The "central IdP" is an assumption. We design for both worlds; the deployment chooses one based on RealPage's reality.

Mode A · Recommended (if available)
Centralized IdP
Federation through Okta or Entra ID

Single login at RealPage's IdP; tokens exchanged into per-system credentials. SSO across all three MCP servers.

  • ✓Cognito brokers OIDC; access tokens carry user claims
  • ✓RFC 8693 token exchange to Fusion (OCI IAM-bound JWT)
  • ✓SAML 2.0 SP-init to Coupa (JIT user)
  • ✓Workforce Identity Federation to BigQuery
  • ✓Single login, single audit identity, single offboarding
Trade-off: requires existing IdP + admin willingness to add 3 SAML/OIDC apps.
Mode B · Fallback
Per-system native auth
MCP inherits each system's identity

No central IdP? Each MCP relies on the upstream's own auth. Users link an account per system on first use.

  • →Oracle Fusion: users login to OCI IAM domain via Fusion's native page; MCP holds OCI access & refresh tokens (encrypted in Secrets Manager).
  • →Coupa: users authenticate via Coupa's local user store or Coupa's tenant-level SAML; MCP exchanges OIDC code per user.
  • →BigQuery: users login with their Google identity; MCP triggers gcloud auth login equivalent flow, stores Google refresh token.
  • ✓Each tool call still inherits the upstream RBAC of that user.
Trade-off: 3 distinct logins, 3 separate audit identities, more token plumbing — but works without central IdP investment.
Switching modes is a config flag, not a rewrite. The MCP edge supports both — Mode A is the default in our IaC; Mode B is a per-system override block. We confirm the decision in Week 1 discovery.

Slide 11 · RBAC & Audit

Inherited, never re-implemented

Principle 1
No new permission model

Every tool call is bound to the human user via OBO tokens (Mode A) or per-system identity (Mode B). The upstream system's RBAC engine is the source of truth — Fusion roles, Coupa user permissions, BigQuery IAM & row-access policies.

Principle 2
Defense-in-depth at the MCP edge

Tool registration carries an explicit scope contract (e.g. core.requisitions.write). Default-deny on unknown scopes. Human-in-the-loop required on all write tools (create / approve / cancel).

Principle 3
Every tool call, immutably audited

Caller identity, tool, args hash, scopes, latency, upstream status — written to S3 with Object Lock (7-year retention). CloudWatch alarms on anomaly patterns; optional SIEM forwarding.
