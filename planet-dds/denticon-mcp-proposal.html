02 · Executive summary

The three takeaways before we go deep

Denticon MCP POC · v0.1

Denticon already runs on the right substrate to host a production-grade MCP server. The hard call is not whether to build it — it's how to wire the data plane and where the semantic catalog lives.

01 · Substrate

The foundations are already in place

Azure APIM fronting your developer portal, an Identity Server issuing JWT claims, an Entra-friendly auth model, and a four-tier multi-tenant data model (PGID → OID → RPID → Patient) mean a remote MCP server slots in alongside what you have — not on top of a rebuild.

02 · The choice

Two legitimate paths, different trade spaces

Option A: wrap the existing public APIs. Inherit auth, billing, semantics. Accept that the analytical surface is bounded by what the APIs expose. Option B: read directly from the SQL replicas. Get the whole column space and analytical joins, at the cost of rebuilding tenant scoping and the semantic layer from scratch.

03 · Scope

Read-only, partner-facing, analytical

The POC stays on read replicas and on read-only API surfaces — no writes, no transactional path. The shipping decision is less “API vs DB” than “which path makes the data dictionary work easier, fastest, with the lowest tenant-isolation risk.”

Our recommendation for this deck:  run both paths as parallel spikes for the first two weeks, then converge on the path with the better prompt-eval score on a shared test set. The investment to run both in parallel is small relative to the cost of choosing wrong.

03 · Why now

MCP has crossed the threshold — and Denticon is already on the curve

Market context

The protocol moment

  • Linux Foundation governance & 18,000+ community servers. MCP has moved from interesting experiment to enterprise infrastructure in twelve months.
  • Streamable HTTP transport (2025-06-18 spec) replaced HTTP+SSE — single-endpoint, stateless-capable, load-balancer friendly.
  • OAuth 2.1 + PKCE, DCR (RFC 7591), Resource Indicators (RFC 8707), Protected Resource Metadata. The authorization story finally matches enterprise expectations.
  • Tool-level scopes (SEP-835, June 2025) and token exchange (RFC 8693) at trust boundaries give multi-tenant MCP a clean isolation model.
  • Microsoft, Anthropic, Google, OpenAI all ship MCP clients now. Building a server is building to a market, not a vendor.

The Denticon moment

Already shipped

DentalOS AI Agents

Confirmation Agent (15–30% no-show reduction) and Scheduling Agent already live inside Denticon and Cloud 9. Internal validation that AI agents working against your data model creates measurable practice value.

Already on Azure APIM

Developer portal at developer.planetdds.com

The portal is “Powered by Azure API Management”. APIM natively supports exposing REST APIs as MCP servers and validating Entra-issued JWTs — significant zero-day leverage.

Already in the market

Third-party AI integrations

Resonate, TensorLinks, Kickcall, and others are already shipping AI receptionists on top of Denticon APIs. A partner-facing MCP standardizes their integration model and reduces support load.

04 · POC objectives

What we're proving — and what we are not

Scope & success criteria

In scope

  • Prompt-to-response over Denticon data via a remote MCP server hosted on Azure.
  • Auth reuse — existing Identity Server JWTs flow end-to-end; no parallel identity system.
  • Tenant isolation — PGID and OID claims enforced at every layer, validated by an adversarial test harness.
  • Read-only, analytical workloads — augment existing reports with conversational data access.
  • Two parallel architecture spikes (Option A and Option B) measured on a shared prompt-eval set.
  • Cross-region DR posture — MCP deploys symmetrically into the Central + East stamps and survives a stamp failover.
  • Audit & observability — every tool call logged with caller, tenant, parameters (PHI-redacted), latency, outcome.

Out of scope (this POC)

  • Writes / transactional flows. No appointment booking, no patient updates, no ledger writes through MCP in the POC.
  • New user identity primitives. The POC consumes existing IdP tokens — no new user store, no new password flows.
  • Cross-tenant analytics for Planet DDS itself. Aggregate views across PGIDs require a separate authorization model; we'll note it but not build it.
  • Production-ready billing meter. POC uses a carve-out; production metering is a separate decision after we have usage data.
  • Embedded Denticon UI integration. POC is a partner-facing remote server; embedded surfaces can be added later without re-architecting.

07 · MCP refresher

The parts of MCP that matter for this design

Spec at a glance

Transport & protocol

Streamable HTTP
Replaces HTTP+SSE since the 2025-03-26 spec. Single endpoint /mcp, stateless-capable, plays nicely with load balancers, proxies, and corporate firewalls.
JSON-RPC 2.0
Message format. Tool calls in, tool results out. Errors are structured. Easy to log and replay.
Three primitives
Tools (functions the client invokes), resources (read-only context blobs), prompts (templates). APIM's MCP server support currently covers tools only — that's exactly what we need.

Identity & authorization

OAuth 2.1 + PKCE
The mandatory baseline. Clients obtain tokens through standard authorization flows; no bespoke MCP auth scheme.
Dynamic Client Registration (RFC 7591)
Optional but powerful — MCP clients can register themselves with your authorization server without manual provisioning.
Protected Resource Metadata
The MCP server publishes a well-known endpoint advertising its authorization server. Clients discover, then dance.
Resource Indicators (RFC 8707)
Tokens are bound to aud=denticon-mcp so a leaked token cannot be replayed against other Denticon resources.

What the 2025-06-18 spec change unlocks

  • Tool-level scopes (SEP-835). Authorization can be expressed per-tool, not just per-server — e.g., denticon.appointments:read distinct from denticon.rcm:read.
  • Token exchange (RFC 8693) at trust boundaries. Tokens received by the MCP server are exchanged for narrower tokens before being passed to backends. The chain of custody is auditable.
  • Closed the “rogue server token leak” class of attacks that haunted early remote MCP deployments. The protocol is now safe enough for partner-facing exposure.

What this means concretely for Denticon

Design implication

The MCP server is “just another API” behind APIM. Your existing validate-jwt policies, rate limit policies, subscription key model, and observability stack all apply. There's no new identity primitive to introduce.

Tool-level scopes give us a clean tenancy model. A token carries scopes like denticon.appointments:read; APIM enforces the scope claim before the request reaches the MCP server; the MCP server then enforces PGID/OID inside the tool itself.

Why this path is attractive

  • Inherits auth, authorization, billing. The token validation, rate limits, quotas, and per-API claims you've already built work unchanged.
  • Inherits semantics. Verbose OpenAPI descriptions become high-quality MCP tool descriptions — the dominant accuracy lever for LLMs.
  • Compliance delta is small. Existing HIPAA posture for the APIs covers MCP-mediated access the same way.
  • Smaller blast radius. Bugs in the MCP layer can't accidentally bypass tenancy — the underlying API enforces.
  • Stable contract. When you version your APIs, MCP versions naturally with them.
  • Familiar to partners. Resonate / Kickcall / TensorLinks already integrate against these APIs — they understand the model.

Where it gets uncomfortable

  • Coverage gaps. Not every column in the DB is exposed via the public API. Analytical questions like “what was last quarter's hygiene production by hygienist by office?” may need composition across multiple endpoints — or aren't currently expressible.
  • Transactional shape, analytical question. The APIs were designed for record-level CRUD. Aggregations, joins, and window functions are an awkward fit; some require multiple round-trips.
  • Fan-out cost. A single prompt can fan out to N API calls — the per-request meter becomes a meaningful billing surface.
  • API enhancement queue. Tools that need new shapes (e.g., batched availability scans across thousands of slots) may need API additions before the tool can ship.
  • Open: Agentic API coverage. Is the hidden agentic surface in scope for wrapping, or does it remain Denticon-internal?

Example prompts → tools invoked

Sample promptTool chain (Option B)

Why this path is attractive

  • Complete column coverage. Every column on the ledger — and the ~50 in 100 that matter — is reachable. Custom insights beyond pre-built reports become a one-tool conversation.
  • Analytical joins and aggregates are first-class. Aging, utilization, production-by-procedure don't require N round-trips.
  • Performance tuning is in our hands. Columnstore, indexed views, query plan inspection — all available on the replicas without affecting transactional workloads.
  • Future-proofs the analytical surface. Adding a new tool = adding one template + one catalog entry; no API release cycle.

Where it gets uncomfortable

  • Tenant isolation becomes our burden. No application-layer safety net. The 3-layer model (slide 15) must hold; we own all three layers.
  • Semantic catalog is real work. The Ledger alone is ~100 cols with ~50 business-relevant. Multiplied across appointments, claims, treatment plans — a serious documentation effort. Without the catalog, accuracy degrades fast.
  • HIPAA / audit posture is a new path. Audit logging, PHI redaction, immutable retention, and BAA scope all need explicit design — not inheritable from the existing API plane.
  • Billing model has no obvious anchor. No per-API meter to inherit; a tool-call meter at APIM is the likely production answer.
  • Reverse compatibility with API changes. If a column's semantics evolve, the catalog and tools must update in lockstep.

16 · Semantic layer · part 1 of 2

The catalog is the accuracy lever — don't underestimate it

Data dictionary & LLM grounding

What the catalog has to do

  • Map prompt → entity. “Michael” — patient, provider, office name, responsible party? The catalog encodes which entity types are searchable for a given phrase shape.
  • Map column → business term. LDG.AMT_DUE is “outstanding patient balance”. APT.STAT_CD is the appointment status code with enum decoding. A column without a description is a column the LLM will hallucinate against.
  • Encode units & semantics. Currency, percentages, statuses, dates with timezone behavior, ADA procedure codes — each gets a typed annotation.
  • Pre-vet examples. Each tool ships with 2–3 example prompts + expected output shape — the strongest few-shot signal we can give the LLM.
  • Disambiguate on entity collision. The catalog adds a classifier prompt step: “Michael is most likely a [patient · provider · office]” before the actual tool fires.

Tooling choices for the POC

  • Source of truth · OSI-aligned YAML in git. No DB writes. The catalog repo is the canonical surface; the schema is read-only ground truth that CI cross-checks against. Built on the Open Semantic Interchange spec (Jan 2026) for vendor-neutral durability.
  • Authoring · LLM-assisted drafts with human review. An offline pass introspects the replica and drafts column descriptions from (column name, type, sample values, FK context); humans approve in a PR queue. Drops authoring cost from minutes to seconds per column.
  • Runtime · Microsoft SQL MCP Server (DAB 1.7). Native describe_entities MCP tool reads our YAML as its description source; ships with Redis cache, Entra integration, App Insights telemetry.

→ See slide 17 for the end-to-end architecture: authoring pipeline, governance, runtime serve, MCP surface.

18 · Observability & compliance

Telemetry, audit, and HIPAA posture

What we log · what we don't

Observability stack

  • Azure Application Insights — end-to-end distributed traces; correlation IDs flow from MCP client through APIM, MCP server, backend.
  • Custom dimensions per tool call: tool_name, pgid_hash (never raw), oid_count, duration_ms, outcome, tokens_used (if known).
  • APIM diagnostic logs → Log Analytics workspace per region.
  • Prompt-eval suite emits a labeled metric per case → live dashboard for accuracy regression detection.
  • Per-tool dashboards — invocation rate, error rate, p50/p95/p99 latency, top-error reasons.

Audit log (HIPAA-aligned)

Every tool invocation emits a structured audit event:

{
  "ts": "2026-05-13T14:22:18Z",
  "correlation_id": "0bf9c2-...",
  "sub": "usr_3409",
  "pgid": 1042,
  "oid_requested": 87,
  "oid_allowed": [7,11,23,87],
  "tool": "denticon.production.summary",
  "params": { "date_range": "Q1-2026",
              "office_id": 87 },
  "outcome": "200",
  "duration_ms": 412,
  "row_count": 17
}

PHI never enters the audit event. Parameters are sanitized; row contents never logged.

HIPAA & PHI posture

  • BAA — assumes existing Microsoft Azure BAA covers new Container Apps / APIM resources (to confirm with Mike).
  • Encryption at rest — Azure-managed encryption for default services; CMK in Managed HSM for any PHI-adjacent caches.
  • Encryption in transit — TLS 1.2+ end-to-end · Private Endpoints where possible.
  • PHI redaction middleware at the MCP server boundary — names, SSNs, DOBs scrubbed from any log line.
  • Network — VNet integration, Private DNS for backend services, restricted egress from MCP server.
  • Identity — Managed Identity for service-to-service · no static secrets in container env.
  • Retention — audit logs into immutable storage with 6+ year retention.
  • Defender for Cloud · Microsoft Purview for governance hooks.
